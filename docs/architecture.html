Document d’architecture

Comment Alfred est construit

Alfred est une application de bureau (Tauri 2, React 19, Rust) livrée vide. L’utilisateur la construit en parlant à un agent de code : pages, fonctions, tables, services, webhooks et planifications vivent dans un dossier d’espace sous git, rangé par modules. Cette page décrit chaque couche, chaque service et leur façon de s’assembler.

Coquille (interface d’Alfred) Cadres isolés (pages, fonctions) Backend Rust (services) Stockage Agents

En démo

Quatre usages, joués dans une fenêtre d’Alfred reconstituée d’après l’application : créer une page en parlant à l’agent, importer un module et le configurer, rechercher puis retrouver sa recherche, corriger un élément d’un geste. Les écrans reprennent les libellés de l’application ; les données sont fictives.

1. Les couches

Cinq couches empilées. En haut, la coquille : la fenêtre d’Alfred, son menu, la page Agent, les Réglages. Elle accueille les cadres isolés, où tournent les pages et les fonctions que l’agent écrit, sans réseau ni disque. Tout ce qui sort d’un cadre passe par un seul pont jusqu’au backend Rust, qui vérifie les accords puis rend le service demandé. Le backend seul touche au stockage. À droite, les agents de code agissent sur la structure par les outils MCP d’Alfred et écrivent le contenu comme des fichiers.

2. L’espace de travail

L’espace est le dossier de l’application que l’utilisateur construit ; il peut en avoir plusieurs, sans lien entre eux. Tout y est rangé par module. La navigation affichée se calcule à partir des manifestes des modules et de alfred.json. Ce que l’agent écrit est versionné ; les données, les fichiers et les copies restent hors de git, dans .alfred/.

Hors de l’espace, Alfred garde sa propre base (réglages, accords, journal, index des conversations, résultats des tests, secrets des webhooks) et range les secrets du coffre dans le trousseau du système. L’agent, qui écrit dans l’espace, ne peut atteindre ni l’une ni l’autre (section 18).

3. Fenêtre et zones d’une page

Une entrée du menu de gauche est une section ; ses pages sont ses onglets, dans la barre du haut. Chaque page peut avoir un panneau de droite, qui est une autre page et reçoit sa sélection. Les Réglages s’ouvrent dans une fenêtre à part, avec les rubriques d’Alfred puis les pages de l’espace qui y sont placées. Une page peut aussi s’ouvrir seule, dans sa propre fenêtre.

Le composant Page découpe la page en zones. Aucune n’est obligatoire et chacune accepte un contenu libre.

La page se souvient. Un cadre est détruit quand on change d’onglet. Ce que l’utilisateur avait tapé ou choisi (recherche, filtres, vue, ligne ouverte) se garde par usePageState(clé, valeur) : la coquille le garde pour la page et le lui rend au retour. CollectionPage le fait seule. Ce qui doit durer au-delà du lancement va en base.

4. Créer une page

L’utilisateur décrit ce qu’il veut ; l’agent fait le reste, sans rien lui laisser à finir. Il agit sur la structure par les outils MCP (placer une page, déclarer une fonction) et écrit le contenu comme des fichiers. Il ne rend la main qu’une fois check passé et la page vue en capture. Chaque tour d’agent devient un commit de l’espace, que l’on peut annuler.

5. Le cadre isolé et le pont

Une page est un composant React affiché dans une iframe sandbox="allow-scripts allow-forms", servie par le protocole alfred-page avec une politique default-src 'none'. Elle n’a pas d’origine, donc ni localStorage ni cookies ; pas de réseau ; WebRTC est coupé dans la webview elle-même. Une fonction tourne dans un cadre invisible du même type. Tout passe par @alfred/sdk, qui envoie un message à la coquille ; la coquille connaît l’identité du cadre (module/page) et la transmet au backend, qui vérifie l’accord avant de servir.

6. Les composants

La coquille et les pages de l’espace utilisent exactement la même bibliothèque, @alfred/ui ; une page n’importe rien d’autre pour son apparence. Elle emploie les composants, elle ne les dessine pas : un besoin absent se compose avec eux. DESIGN.md en donne l’usage ; check signale un style propre.

8. Les données d’un module

Chaque module a ses tables dans la base de l’espace, préfixées par son identifiant ; il les crée par des fichiers de migration versionnés avec lui. Les tables d’Alfred portent le préfixe _alfred_ : le module ne peut ni les lire, ni les modifier, ni les imiter. C’est là que vivent l’historique, les index de recherche et la file de la recherche par le sens.

9. Recherche plein texte

Le module déclare ses index dans search de module.json. Alfred crée une table FTS5 à contenu externe et les déclencheurs qui la tiennent à jour à chaque écriture, puis la reconstruit quand la déclaration ou la table change. La page n’a qu’à demander.

10. Recherche par le sens

Retrouver des lignes par ce qu’elles veulent dire : « facture d’électricité » trouve « note EDF de mars ». Alfred calcule pour chaque ligne un vecteur avec un modèle local, multilingual-e5-small (français compris), exécuté en Rust par candle. Le modèle, environ 470 Mo, est livré avec Alfred dans ses ressources. Il est rangé dans le dépôt lui-même, découpé en morceaux que la construction recolle, empreintes vérifiées : personne n’a rien à télécharger, ni l’utilisateur, ni le développeur, ni la CI.

11. Fichiers et documents

Une page n’a pas de disque : elle confie ses fichiers à Alfred, qui les range dans le dossier du module, hors de git, avec leurs métadonnées. Chaque module ne voit que les siens. Alfred sait aussi produire des documents (un PDF écrit sans dépendance, un CSV, un classeur Excel) et lire le texte d’un PDF ou d’un Word.

12. Fonctions et automatisations

Une fonction est déclarée dans le manifeste de son module. Pages, agents, webhooks, planification, événements et tâches de fond l’appellent tous de la même façon. Une fonction TypeScript tourne dans un cadre invisible, avec le même pont qu’une page ; une fonction en script (bash, PowerShell, Python) est un vrai processus, qui lit son entrée en JSON sur stdin et rend sa sortie sur stdout, avec un jeton à usage unique pour appeler le même SDK.

Événements entre modules

Un module publie un événement qu’il a déclaré ; ceux qui s’y abonnent le reçoivent dans une de leurs fonctions. Le module qui publie ne connaît pas ses abonnés : c’est ce qui remplace l’appel direct à un autre module.

Tâches de fond

Un travail long (importer des milliers de lignes, relever tout un service) est découpé en étapes. Alfred rappelle la fonction étape par étape, chacune sous les 120 secondes, en lui rendant l’état qu’elle a laissé. Cet état est gardé en base : une tâche interrompue reprend où elle s’était arrêtée, et l’utilisateur peut l’annuler entre deux étapes, depuis la fiche du module. La planification, elle, repose sur l’horloge d’Alfred ouvert : une heure fixe manquée part au premier réveil du même jour.

13. Services extérieurs et coffre

Pages et fonctions n’ont pas de réseau. Une fonction nomme un client ; Alfred exécute la requête et y ajoute l’authentification lue dans le coffre. Le fichier d’un client est versionné avec l’espace et ne contient donc aucun secret : seulement l’adresse, les façons de s’authentifier et, pour chaque compte, l’entrée du coffre à utiliser.

14. Configuration d’un module

Un module importé d’un marketplace ouvre un parcours de configuration. Le module fixe la façon de se connecter : l’agent qui l’a écrit décrit chaque service en entier. L’utilisateur n’ajoute que ses comptes. Le parcours se déduit de ce que le module déclare et de l’état réel des services : rien n’est mémorisé à part les résultats des tests, et il reprend toujours à la première étape incomplète.

15. Agents de code et MCP

Alfred ne contient pas son propre modèle de code : il pilote les agents déjà installés sur le poste (Claude Code, Codex, OpenCode). La coquille parle le protocole de chaque CLI ligne à ligne, à travers un processus lancé par Rust ; elle nomme un harnais et des options connues, jamais un programme ou des arguments libres. L’agent atteint Alfred par un serveur MCP local.

16. L’IA dans une page

Une page peut se servir d’un modèle de trois façons, de la plus simple à la plus libre.

17. Partage : git, équipe, marketplace

Trois usages de git, trois dépôts différents. L’accès distant repose sur les identifiants déjà configurés sur le poste (gestionnaire d’identifiants, agent SSH) ; Alfred n’exécute aucun crochet et refuse un dépôt dont la configuration ferait lancer un programme.

18. Accords et secrets

L’agent écrit dans l’espace ; il ne doit donc rien pouvoir y écrire qui lui donne un droit. Tout ce qui décide d’un accès vit hors de l’espace.

19. La voix

Dictée et lecture à voix haute, sur l’ordinateur. Un seul micro pour toute l’application : la page Agent ou une page de l’espace l’ouvre, et seul celui qui l’a ouvert peut le fermer. La lecture est une file unique ; une nouvelle lecture coupe la précédente.
